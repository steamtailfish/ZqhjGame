## 3. 赛题二到底要求什么

**[手册＋源码]**

- 3架无人机，每架独立Agent；3个真实地面目标、15个移动诱饵；一个回合600仿真秒。
- 至少2架飞机同时有效跟踪同一真目标，持续20秒后判定清除。
- 中断不超过2秒，恢复后保留并回补；超过2秒，累计跟踪时间清零。
- 真目标清除后停车，诱饵不因此停车；Agent没有目标清除标志，停车也需要结合不确定性判断。
- 真目标和诱饵都可移动，不能直接把“运动”视为真目标标签。
- 飞行高度固定500m，速度15–40m/s，FOV5–50度；文档规定最大转弯率30度/秒。
- 机间距应避免小于200m；越出地形边界500m后有惩罚。正式描述与本地惩罚算法存在差异，见后文。
- 通信有效载荷最多50字节UTF-8，发送上限4Hz；本赛题地图范围内通信距离不限。
- 坐标上报是单独的report_target接口，影响精度评分；广播坐标不会自动变成有效上报。
- 手册最终考评说明为客观90%、创新10%，并有新路线验证；不能只对一个本地种子有效。

没有把赛题三的防空、干扰区、10目标或生存评分加入本赛题要求。通用SDK包含相关字段，并不证明当前赛题二存在这些威胁。

## 4. 已核验的真实SDK

### 4.1 入口、生命周期和调用时间

实际链路为：

```text
项目启动器（统一工作目录、模块路径和运行证据）
→ python -m competition run --scenario coop_decoy --agent module:Class
→ 赛题二runner准备场景副本并启动官方引擎
→ 等待引擎订阅/首帧、注入3真车和15诱饵的A*运动
→ 分别创建3个Agent、configure、reset
→ 本机隔离观测 → sensor/默认感知 → decide
→ 导航/云台/通信命令发引擎，report_target交裁判
→ 几何跟踪判定、清除、上报精度和惩罚
→ 官方evaluation.json
```

- 基类：`competition.sdk.scenarios.coop_decoy.CoopAgent`。
- 构造：`Agent(my_uid: str)`；同一Python进程中创建3个独立对象，按机顺序调用，不能借助全局变量共享状态。
- 生命周期：configure(config)→reset()→sensor(obs,dt)→decide(obs,dt)。当前这条CLI链路给configure的是`{}`，未自动加载场景旁algorithm.yaml。
- 名义控制频率10Hz；传入dt固定0.1。**不是实际墙钟或仿真经过时间**。
- 合法相对仿真时间可从briefing.score_view.sim_time读取；首拍score_view=None。后续分数来自前一拍，sim_time为本次帧的相对时间。
- 标准加载是`module:Class`；项目通过统一PYTHONPATH暴露src，不用修改官方competition目录。

### 4.2 Agent实际看得到什么

顶层仅有`obs.self`、`obs.comm_inbox`、`obs.briefing`。

| 信息 | 实际情况 |
| --- | --- |
| 本机状态 | uid、WGS84经纬度、alt、heading_deg、标量speed、云台pan/tilt/FOV、status、jammed、通信统计 |
| detection | detected、confidence、target_lat、target_lon、azimuth_error_deg、target_type |
| 目标位置 | 识别层输出的含噪经纬度，可缺失；不是合法暴露的真值 |
| 目标ID | Detection里没有稳定目标ID；需自己做临时轨迹关联 |
| 目标类别 | target_type可能将诱饵伪装为ground_vehicle，不能作为可靠真伪标签 |
| 目标动态 | 没有目标速度、未来路线、每目标清除标志或跟踪累计时间 |
| 队友状态 | 没有队友坐标或完整状态，只能通过队友通信载荷获得 |
| photo | bytes或None；合法图像字段存在，但本机三路图像尚未验证；没有公开深度图字段 |
| detections复数 | 多结果时填入；仅一个结果时可能仍为空，不能忽略单数detection |
| briefing | 本机ID、编队数量、任务区域、目标总数、静态参数、聚合score_view等 |
| 聚合成绩 | 总分、维度分、清除总数、目标总数、passed、相对仿真秒；不含哪个目标被清除 |

没有公开加速度、完整姿态四元数、推力等信息；不能直接将YOPO里程计输入与这些观测逐项对应。

### 4.3 可用命令

```python
fly_to(lat, lon, alt=None, speed=None,
       loiter_radius=200.0, turn_direction="right")
set_heading(heading_deg)
set_speed(speed)
point_gimbal(pan_deg, tilt_deg)
set_gimbal_fov(fov_deg)
broadcast(payload: str)
send_to(peer_uid: str, payload: str)
report_target(lat, lon, target_id=None)
```

没有姿态、推力、任意加速度或直接执行三维多项式轨迹的公开比赛接口。fly_to到点盘旋，文档说明alt被忽略。当前应按受限平面运动与独立云台建模，不能直接假设四旋翼悬停或任意三维机动。

普通命令按返回顺序发布；同类命令互相覆盖的完整物理细节尚未验证。report_target有明确特例：**每机每拍只取最后一条**。

### 4.4 通信的重要实测

- payload必须为字符串，Python构造器按UTF-8编码后字节数检查50字节上限，非50个中文字符。
- Message仅含sender_uid、payload、recv_time。
- **[实测]** 收件箱保留最多32条历史消息，跨帧重复出现，SDK没有自动消费/去重。
- **[实测]** 广播消息也出现在发送者自身收件箱；通信统计为累计增长，不是每拍增量。
- 需要序号/时间、TTL、去重和自消息处理，但这些自研逻辑尚未实现。
- 4Hz底层窗口边界、定向发给无效ID、溢出队列的精确处理仍待确认。

## 5. 感知、图像与识别瓶颈

**[源码]** train默认使用AccuracySimulator，从内部几何检测生成漏检和含噪位置；默认accuracy=.85、noise_sigma_m=50。本场景天气Snow_Light使基础检出概率变成.7225、每轴位置噪声sigma变成75m；水平距离1000m以内不额外衰减，1000–3000m线性降至0。该模式不等于训练了我们的算法。

**[源码＋实测范围]** UE增强包提供photo入口，但本轮没有启动UE、获取三机图像、下载YOLO模型或跑eval。PhotoCache没有暴露帧时间戳或失效TTL，没有新图时可能复用旧图。SDK文档称PNG，实际传输格式、新鲜度和三机归属未验证。当前默认YoloDetector构造绑定首机，不能假设三机eval视觉链路已正确支持。

**[分析]** 当前没有证据证明，仅靠被伪装的target_type和运动历史，就能可靠地区分真车与移动诱饵。非视觉策略可以先验证运动、消息和K=2协同，但“协同能清除一次”不代表已解决比赛的识别问题。

这一点是技术路线的重要分岔：若视觉是真伪辨别必需的信息源，那么图像通路验证应成为早期工作；若暂以train模式建立控制基准，应明确其局限，不能让便利的模拟感知代替最终识别验收。

## 6. 官方评分及实现冲突

当前真正运行的是`competition/sdk/_vendored/coop_eval.py`，不是examples目录里的旧副本。

- **清除**：裁判使用引擎几何检测和内部真值做目标关联，至少两机有效跟踪才累计时间。Agent自研sensor的置信度并不直接驱动清除计时。
- **上报**：将报告位置关联到最近存活真目标，target_id标签不决定分桶；若更靠近已清除目标，则报告被丢弃。所有飞机对同一裁判目标共享每秒1条配额。
- **精度**：每个真目标分别计算RMSE，分项为`max(0, 1-RMSE/120m)`，未上报目标计0，再按目标平均；清除后冻结此前累积。
- **权重**：kill50%、accuracy30%、mission_time20%。手册规定全歼相对240秒内时间满分，240–420秒线性降至0，未全歼时间分0。
- **本地最终分**：惩罚前基础分减惩罚，截断至0–100。passed用基础分≥70且完成率≥2/3判断，不等于程序是否成功退出或正式晋级规则。
- **输出限制**：JSON有总体RMSE和上报数，per_target有清除/跟踪诊断；不输出逐目标上报数和RMSE。不能从总体值还原这些分桶。

需要保留的冲突：

| 冲突 | 本地证据 | 对决策的影响 |
| --- | --- | --- |
| 惩罚口径 | 手册描述持续累计、越近扣越多；源码按进入违规状态计次，每次2分、总封15，持续不重复加 | 策略遵守安全间距，不利用本地持续违规只扣一次；正式口径待确认 |
| 任务时间原点 | 引擎原始时间实测从-28800起；裁判全歼时刻未减原点就与240/420比较 | 合成同样第300秒全歼，原点0/-28800/大正数得到不同time分；不得修评分或利用此缺陷 |
| 边界 | briefing任务区域和裁判地形矩形不一致 | 边界约束要区分来源，不能把任一当无争议正式合同 |
| 云台角度/速率 | 文档称瞬时；通用配置仍列速率；基线相对机头pan和辅助反算函数约定存在差异 | 需真实小实验核验；不直接复制坐标转换 |
| 固定种子 | 真目标路线等部分初始化与seed有关；诱饵路线、感知随机数未完全固定 | 运行命令可复现，不保证同seed逐帧或同分 |

本地仿真成绩与正式比赛规则不同之处要如实记录，不能让本地实现覆盖手册。

## 9. YOPO与YOPOv2-Tracker：已读到的内容

用户提出以以下两篇论文的思路作为技术方向。Codex已读取两篇全文及关键架构/实验图，仅做只读评估。

### 9.1 第一篇：YOPO，2024

论文：You Only Plan Once: A Learning-Based One-Stage Planner With Guidance Learning，IEEE RA-L 2024，9(7):6083–6090，8页；DOI：10.1109/LRA.2024.3399589。

**[论文，第3–5页]**

- 面向四旋翼在密集障碍环境中的局部导航。
- 输入深度图、速度/加速度、目标方向。
- 在视野中布置多个运动原语，一次网络前向预测每个候选的终态调整及评分，再执行最优候选。
- 以五次多项式表示轨迹，持续滚动重规划。“Only Plan Once”不是全任务只规划一次。
- guidance learning把平滑、避障、目标引导等轨迹代价梯度反传至网络；训练评价使用特权环境信息，在线网络仍只能看局部输入。
- 实验采用深度相机和近距离障碍环境；其推理速度/导航实验不直接证明本赛题适用。

### 9.2 第二篇：YOPOv2-Tracker，2025

论文：YOPOv2-Tracker: An End-to-End Agile Tracking and Navigation Framework from Perception to Action，arXiv:2505.06923v1，2025-05-11，19页。

**[论文，第5–10页]**

- 将目标检测和局部规划结合，输入RGB-D与6维速度/加速度状态。
- 示例输入160×96、90度水平FOV，5×3候选；每候选输出14维，包含轨迹终态、代价、目标位置和objectness。
- 用objectness筛选、EKF状态估计和时空一致性排除错误检测，再选择合适轨迹。
- 虽然不依赖复杂的长时目标路线预测，仍用恒速模型EKF做短时估计与漏检补偿，不能解读为“不需要状态估计”。
- 目标视线朝向与轨迹分别处理；进一步利用四旋翼微分平坦性及扰动观测器输出姿态、推力。
- 训练的objectness主要区分目标与背景，不是本赛题真车与相似移动诱饵的分类器。

**[论文实验范围，第12–15页]** 跟踪对象起始可见；单机跟踪实验对比目标速度3–7m/s、每档10次，真实实验主要为近距离人体跟踪。没有验证未知区域搜索多个真假车辆、限带宽协同、双机20秒规则或坐标上报评分。

## 10. 技术适配：事实与分析分开

| 问题 | 当前可依据的事实 | 尚未验证的适配判断 |
| --- | --- | --- |
| 深度输入 | YOPO依赖深度，Tracker依赖RGB-D；SDK未提供深度字段，RGB图像通路也未验证 | 不能直接用预训练模型；单目深度估计若引入，会新增尺度/误差问题，不等于原传感器 |
| 动作空间 | YOPO是四旋翼3D轨迹/姿态，赛题固定500m并有速度/转弯限制 | 需重新定义合法平面运动原语及云台动作；不能只改输出接口名称 |
| 速度 | 论文有速度归一化；源码加速度按倍率平方放大 | 不能仅把6改为30就宣称满足比赛动力学；需要新的可行性约束 |
| 跟踪目的 | 论文趋向接近目标，赛题需要两机有间距地持续观察地面目标 | 需改为观察位形/可见性/跟踪连续性目标，避免两机向同一点聚集 |
| 图像域 | 论文主要低空近距；赛题500m、FOV5–50度、车辆小目标 | 原低分辨率结构和权重未必能辨车辆细节；缩放/FOV/像素尺度需实测 |
| 多目标真假 | 论文objectness不是真假分类，且不提供本赛题的多目标身份管理 | 需独立研究视觉辨别、轨迹关联和重复目标抑制 |
| 多机协同 | 论文未给本赛题K=2角色分配与50字节通信 | 协同与上报调度仍需自行设计 |
| 训练梯度 | YOPO有轨迹代价梯度，官方评分含阈值、关联、中断和离散事件 | 不能直接把官方总分送入autograd；若学习，需要合理代理目标及真实评分验收 |
| 低延迟收益 | 论文报告毫秒级计算；官方runner名义10Hz、实际时间还受引擎影响 | 降低网络延迟不等于提高整个决策/观测频率，收益需测量 |

训练特权信息的思想只能在符合赛事授权的数据和流程中考虑，不能把隐藏路线、固定身份或未开放状态编码进在线策略。阅读论文中训练用真值的设计，不代表获得了读取比赛隐蔽信息的授权。

## 11. Codex现有建议——待独立评审，不是既定决定

Codex当前倾向如下：

1. 先修好合法观测时间、通信去重和加载/回归基础。
2. 做可验证的云台/运动小闭环和最小双机共同跟踪。
3. 借鉴YOPO的“多个候选＋评价择优”，先用显式代价验证价值，不立即上网络训练。
4. 借鉴Tracker短时估计/一致性筛选，但针对多目标关联重新设计。
5. 只有在图像、动力学、训练数据和验收指标清楚后，再判断是否学习候选评价、轨迹调整或视觉控制。

这份建议的潜在盲点也需要评审：如果可靠识别依赖视觉而视觉链路未通，过早投入大量非视觉协同工作可能延后最关键的信息瓶颈。因此，“先UE图像验证”与“先协同控制闭环”的优先关系，请你明确判断，而不是默认接受现有阶段顺序。
